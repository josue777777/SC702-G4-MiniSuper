# HU-20 — Historial de ventas del día

Issue: https://github.com/josue777777/SC702-G4-MiniSuper/issues/21

Rama: `feat/hu-20-historial-ventas`. Base: `172aed04b06a111a9a5daeb57bdcc2d2de548404`.

## Uso y alcance

En **Ventas › Historial de ventas**, el día inicial es hoy en Costa Rica. Se puede
seleccionar otro día, filtrar por efectivo/tarjeta/fiado, actualizar y recorrer páginas
de 50 ventas. Se muestran número, fecha/hora de Costa Rica (24 horas), productos con
cantidades originales, método, estado, cliente, importe original e importe efectivo.

**Detalle** consulta la venta persistida con sus precios históricos, cantidades
originales y devueltas/anuladas, efectivo recibido, vuelto original, saldo actual del
cliente y auditoría de ajustes. Desde ahí se abre el comprobante de HU-34. Los botones
existentes de comprobante y anulación/devolución de HU-35 siguen disponibles.

Las ventas y ajustes confirmados desde la caja recargan el historial. **Actualizar
historial** consulta cambios de otras sesiones. Durante una consulta o un error no se
presentan filas/totales anteriores como si correspondieran al filtro nuevo.

## Importes

- **Original de una venta:** suma de `SaleItem.unitPrice × quantity`, con el precio
  histórico. Las cantidades de las filas son las originalmente registradas.
- **Efectivo de una venta:** `Sale.total`, mantenido transaccionalmente por HU-35 al
  descontar ajustes. Una venta anulada o completamente devuelta tiene importe cero.
- **Acumulado original del día:** suma del efectivo más todos los importes de
  `SaleAdjustment` asociados a las ventas de ese día. HU-35 conserva cada rebaja y no
  modifica los snapshots originales.
- **Acumulado efectivo del día:** suma de `Sale.total` para todas las ventas del día.
  Incluye fiados; mide ventas después de ajustes, **no ingresos cobrados ni ganancias**.
- Los acumulados y el conteo de ventas del día incluyen todos los métodos y estados,
  independientemente de la página o el filtro de pago. El conteo de coincidencias sí
  aplica el método seleccionado. Anulaciones y devoluciones permanecen para auditoría.
- Se selecciona por **fecha de la venta**, no del ajuste: una devolución posterior
  modifica el efectivo del día original. No es un reporte de flujo de caja por fecha
  de devolución.

## API y arquitectura

Nuevo: `GET /api/sales/daily-history`.

| Parámetro | Validación / valor predeterminado |
| --- | --- |
| `date` | Fecha real `YYYY-MM-DD`; omitido: hoy en `America/Costa_Rica` |
| `paymentMethod` | `CASH`, `CARD` o `CREDIT`; omitido: todos |
| `page` | Entero de 1 a 1 000 000; predeterminado 1 |
| `pageSize` | Entero de 1 a 100; predeterminado 50 |

Respuesta `{ data: { date, page, pageSize, matchingCount, sales, day } }`, donde
`day = { saleCount, originalTotal, total }`. Los importes son cadenas con dos decimales.
Una página fuera del resultado contiene `sales: []` y conserva los agregados reales.

Se mantiene Routes → Controllers → Services → Repositories → Prisma. El servicio
resuelve `[00:00 del día, 00:00 del siguiente)` en Costa Rica, equivalente a
`[06:00Z, 06:00Z del siguiente día)`. El repositorio consulta por negocio y fecha,
con el índice existente `Sale(businessId, createdAt)`, ordena por
`createdAt DESC, number DESC` y pagina.
Filas, conteo y agregados se leen en una transacción `RepeatableRead`, con sumas
PostgreSQL Decimal y operaciones de céntimos `bigint`.

El router existente exige sesión, contraseña propia, negocio activo y permiso
`sales`: Encargado y Cajero; Bodega y Admin no acceden. El negocio se obtiene de la
sesión, nunca de los parámetros. Los ajustes se agregan filtrando por su venta y
negocio. El detalle ajeno devuelve 404.

No cambia el contrato de `GET /api/sales`, `GET /api/sales/:id`,
`GET /api/sales/daily-summary` ni el de los ajustes. El dashboard HU-37 conserva su
lógica y tiene regresión de integración para sus acumulados tras anular/devolver.
No hay cambios de esquema, migraciones nuevas ni dependencias nuevas. Solo se
consulta información existente; HU-20 no persiste datos adicionales.

## Verificación reproducible

Las pruebas de integración solo se activan con `DATABASE_URL` terminado en `_test`;
las E2E exigen `E2E_DATABASE_URL` terminado en `_e2e`. Aplicar las migraciones existentes
a **cada base aislada** con `prisma migrate deploy` antes de ejecutar.

```powershell
$env:DATABASE_URL = '<conexion a base aislada terminada en _test>'
npm test
$env:E2E_DATABASE_URL = '<conexion a base aislada terminada en _e2e>'
$env:EVIDENCE_DIR = 'C:\Users\dagui\Documents\GitHub\SC702-G4-MiniSuper-evidencias\sprint-3'
npm run test:e2e
```

- Validadores: fechas imposibles/bisiestas, métodos y límites de paginación.
- Servicios: cambio de día antes/después de las 06:00 UTC, selección explícita.
- Endpoints: consultas inválidas, orden, más de 50 ventas, acumulados sin truncar,
  protección sin sesión y cookie falsificada.
- PostgreSQL: 62 ventas del día más fronteras excluidas y otro negocio; todos los
  estados; devoluciones posteriores; empates de hora; agregados y detalle aislados;
  precios originales y regresión del resumen HU-37.
- Playwright: tres escenarios nuevos con API, Express, Prisma y PostgreSQL reales.
  Incluyen ventas CASH/CARD/CREDIT, varios productos, detalle/comprobante, ajustes
  desde la interfaz, filtros, páginas, medianoche, vacío, error de red/reintento,
  permisos y dos negocios. El navegador usa `Asia/Tokyo` para comprobar que las
  horas y el día siguen correspondiendo a Costa Rica.
- Rendimiento: se mide una recarga completa (respuesta de API y 50 filas renderizadas)
  con 62 ventas del día y se exige menos de 2 segundos. Es una medición local, no una
  garantía sobre cualquier servidor o conexión.

Las capturas se generan mediante `saveEvidence()` después de las aserciones:
`HU-20-historial-ventas-dia.png`, `HU-20-detalle-venta.png` y
`HU-20-total-acumulado.png`, en la carpeta externa `sprint-3/HU-20`.

## Dependencias y límites

Sin placeholders ni dependencias pendientes para HU-20. Se reutilizan los contratos
de ventas, ajustes y comprobante existentes. Código y nombre de producto se consultan
del catálogo como en HU-34; precios y cantidades provienen de la venta histórica.
La zona horaria sigue siendo la fija del proyecto, Costa Rica.
